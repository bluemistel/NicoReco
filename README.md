# NicoReco

ニコニコ動画の「音声合成実況・解説・劇場」ジャンルを対象に、
**評価を重ねながら自分の好みの重みを育てて、候補を絞り込んでいく**ための仕組み。

対象範囲は最初は直近数年だけにしておき、好みが固まってきたら
過去へ、そして高評価動画の周辺へと広げていく。

```
収集（Python / GitHub Actions）           配信（Astro / GitHub Pages）
  ランキング ─┐                              静的JSON
  タグ検索 ──┼→ SQLite ─→ 候補プールJSON ─→ ブラウザ内で学習
  投稿者一覧 ┘                              （localStorage）
```

## なぜこの構成なのか

Snapshot 検索API v2 は **CORS ヘッダを返さない**ため、ブラウザから直接は叩けない。
そこで取得は収集側（手元 or GitHub Actions）に寄せ、
Webアプリには静的JSONだけを配る。結果として、

- 利用者はAPIキーもプロキシも要らない
- GitHub Pages の静的配信だけで完結する
- 好みのデータは各自の端末から出ていかない

## 調査してわかったこと

実際にAPIを叩いて確認した挙動。ドキュメントに書かれていないものも含む。

| 事項 | 結果 |
|---|---|
| Snapshot API のエンドポイント | `https://snapshot.search.nicovideo.jp/api/v2/snapshot/video/contents/search`（GETのみ・APIキー不要） |
| `_limit` / `_offset` | 最大 100 / 最大 100,000。10万件を超える母集団は期間で区切る必要がある |
| CORS | ヘッダなし。ブラウザから直接は不可 |
| ランキングのRSS | `?rss=2.0` は現在HTMLを返す（事実上機能していない） |
| 「音声合成実況・解説・劇場」 | 2025年のランキング改変で新設。genreキーは `wnm2mhv0` |
| Snapshot API の `genre` | 旧16ジャンル体系のまま。新ジャンル名は返らないので、**genre では母集団を作れない** |
| ランキングページ | SSR済みHTMLから動画IDを順位順に抽出できる（1ページ約107件） |
| `contentId` のORフィルタ | 可。ただし100件だと `HTTP 414`。30件ずつに刻んでいる |
| `_sort` | jsonFilter 使用時も省略不可（省略すると `QUERY_PARSE_ERROR`） |
| `userId` フィルタ | **不可**（jsonFilter の許可フィールド外）。投稿者の過去作は nvapi 側で取得する |
| サムネイルURL | 末尾にバージョン番号が付く動画があり、動画IDからは組み立てられない。APIの値を保存している。大きい版は `.L` 付き（古い動画には無い） |
| 投稿者名 | Snapshot API は `userId` しか返さない。名前を返すのは非公式の内部API（nvapi）で、**利用規約 第4条(19)「個人に関する情報の収集、蓄積行為」に触れうるため使わない**。投稿者はIDのみで扱う |
| タイトルの文字 | **HTMLエスケープされたまま返る**（`&quot;` `&amp;` `&gt;`）。保存時に `html.unescape` で戻さないと、表示側で二重にエスケープされて画面に `&quot;` が出る |

## 収集側

```bash
# ランキングから母集団を種まきする
python collector/collect.py ranking --terms 24h week month

# タグで深掘りする（中断しても次回は続きから）
python collector/collect.py tags --tag ゆっくり実況 --max 2000

# 高評価動画の主要タグから探索を広げる（公開用プールでは使わない）
python collector/collect.py expand --liked sm44943000,sm46753898

# 誰かの好みから辿って入った動画を落とす（公開用プールの中立化）
python collector/collect.py prune

# 候補プールを web/public/data/ に書き出す
python collector/export_pool.py --size 8000

# 現状確認
python collector/collect.py stats
```

標準ライブラリだけで動く（依存パッケージなし）。
リクエスト間隔は1秒、429と5xxは指数バックオフ、403は即中断。

### 初期コーパス

`data/nico.db` は既存の「ボイロ劇場分析」の成果物を引き継いでいる。
入口タグ10種・139,019本・2009〜2026年。
スキーマは後方互換マイグレーションで拡張しているので、そのまま置くだけで使える。

既存DBは**タグをタブ区切りで保存していた**（収集側はスペース区切り）。
混在したままだと「タグ全体がひとつの巨大なタグ」として扱われ、
表示が繋がるだけでなく、その動画のタグ特徴が全部失われる。
読み取りは空白文字全般を区切りとして扱うようにしてある
（タグ自体にスペースは入れられない）。

保存済みデータの手当ては `collect.py fix-text` にまとめてある。
タグの区切り揃えと、タイトルのHTMLエスケープ戻しの両方を通す。

`data/*.db` はリポジトリに入れていない（80MB超）。
GitHub Actions では `actions/cache` で持ち越し、
キャッシュが失われた場合はランキング分から作り直しになる。

### 使うAPIの方針

使うのは**公式に提供が確認されている Snapshot 検索API v2 だけ**にしている。
投稿者名・アイコン・投稿者の動画一覧を返す nvapi は非公式の内部APIで、
かつ人に関する情報を集めて配ることになるため、依存を持たない。

ランキングページのHTML読み取りだけは例外で、
このジャンルの母集団を得る手段が他に無いため残している
（1日3リクエスト、取るのは動画IDと順位のみ）。

### 掲載除外と削除の反映

- `collector/optout.txt` — 掲載を望まない方の申し出をここに1行足す。
  動画IDか `user:投稿者ID` を書くと、次の書き出しから候補に入らなくなる
- `export_pool.py` は書き出し前に候補を全件取り直し、
  **APIが返さなくなった動画（削除・非公開）をDBごと落とす**。
  ついでに再生数などのカウンタも最新になる（`--no-verify` で省略可）

### 類似動画の探索（`expand`）

起点の動画群からタグを数え、作品の内容を表さないタグ
（キャラ名・ソフト名など）を除いた上位を `tagsExact` で検索する。
期間を区切って古い側へ掘れる。

**公開用のプールを作る間は使わない。** 誰かの好みが母集団に混ざるため。
使ってしまった場合は `prune` で落とせる。

### 学習しているもの

疎なロジスティック回帰をオンライン（SGD）で更新している。
ニューラルネットではなく線形モデルにしているのは、
**重みをそのまま画面に出して、人が読めるようにするため**。

特徴量:

- タグ（プール内で頻出する語彙のみ。1本しかないタグまで拾うと丸暗記になる）
- 投稿者
- 動画長のビン（〜3分 / 3〜6分 / 6〜12分 / 12〜25分 / 25分〜）
- 投稿年代のビン
- 再生数（対数）・保存率（マイリス＋いいね÷再生）・コメント率 の標準化値

評価は★1〜5（★1→0.0、★5→1.0）。学習率は更新回数に応じて減衰する。

操作は3種類あり、役割をはっきり分けてある。

| 操作 | モデルへの影響 | 候補プールでの扱い |
|---|---|---|
| ★1〜5 | 学習する | 二度と出ない |
| 保留 | **何もしない** | しばらく経つとまた出てくる |
| 投稿者を除外 | 何もしない | その投稿者の動画が全部消える |
| お気に入り投稿者 | 何もしない | 変わらない（あとで見に行くための控え） |

| お気に入りタグ（タグを左クリック） | 重みの下限を敷く | 変わらない |
| 除外タグ（タグを右クリック） | 何もしない | そのタグの動画が全部消える |

「興味がない」は★1で伝える。保留は「今は判断できない」ための操作で、
好みの信号としては一切使わない。代わりに、こちらが何度か判断を重ねた頃に
また候補へ戻ってくる（実時間ではなく行動数を時計にしているので、
再登場時にはモデルが更新済み＝順位も変わっている）。

**何も押さずに「次のバッチへ」を押した場合、残りは全部保留になる。**
そのまま候補へ返すと、次のバッチでも同じ顔ぶれが上位に来てしまうため。

復帰までの行動数は `14 × 保留回数 + 0〜40 の乱数` でばらけさせている。
まとめて保留したぶんが揃って戻ってくると、同じバッチが再現してしまう。
さらに、一度見送った動画が1バッチを占領しないよう、
復帰組の枠を全体の3割までに制限している。

### お気に入りタグ

好きなジャンルのタグでも、たまたま合わない動画が続けば重みは下がっていく。
カードのタグをクリックするとお気に入りになり、そのタグの重みは
`PIN_FLOOR`（+0.30）より下に落ちなくなる。

下限に張り付いている間も他の特徴は普通に動くので、
「そのタグは好きだが、この動画が嫌いな理由は別にある」という形で
投稿者・動画長・年代のほうへ負の信号が寄っていく。

### 除外タグ

タグを**右クリック**すると除外になり、そのタグが付いた動画は
候補から丸ごと消える。投稿者の除外と同じ扱いで、好みの学習には触らない。
右パネルに「何本消しているか」が出て、いつでも解除できる。
お気に入りと除外は同じタグに同時には付かない（後から付けたほうが勝つ）。

### 候補のリセット

「候補をリセット」は、**学習した好み・お気に入り・除外を残したまま**、
評価済みと保留の記録だけを消す。育った重みで同じ母集団をもう一周できる。
「やり直す」は全部消して最初からになる。

投稿者の除外は評価とは無関係の、候補を機械的に減らすための操作。
多作な投稿者が趣味に合わない場合、1回の操作で数十本を候補から外せる。
右パネルからいつでも解除できる。

お気に入りはその裏返しだが、**候補の出方は変えない**。
同じ投稿者でも作品ごとに立ち絵や作風が違うことがあるので、
「この人は追いたい」を重みに混ぜてしまうと判断が鈍る。
右パネルに一覧が残り、投稿者ページへのリンクと、
その投稿者の作品を丸ごと取り込む `uploader` コマンドが出る。

投稿者名とアイコンはカードのタイトル直下に出る。
名前がまだ取れていない投稿者は投稿者IDで表示され、
`collect.py users --from-pool` を回すと順に埋まる。

### 探索

好みスコアだけで並べると数周で同じ傾向しか出てこなくなるので、
まだ評価していない特徴ほど大きくなる不確実性ボーナスを足している。
右パネルの「探索の強さ」で比率を変えられる（0にすると好み一直線）。

同じ投稿者が1バッチに3本以上入らないようにもしている。

### 表示中のバッチを覚えている

動画リンクは `target="_blank"` で開くが、埋め込みブラウザなど
これを無視して同じ画面で遷移する環境があるので、JS側でも
`window.open` を明示的に呼んでいる。

そのうえで、表示中の10本（並び順・バッチ番号・各カードの判定）を
プロファイルに保存している。提示は探索のゆらぎを含むため、
作り直すと別の並びになってしまう。同じ画面で遷移して戻ってきても、
リロードしても、見比べていた候補がそのまま残る。

### 保存先

評価・重み・設定はすべて `localStorage`（キー `nicoreco.profile.v1`）。
サーバーは無い。書き出したJSONを別端末で読み込めば移行でき、
そのまま収集側の `expand --profile` に渡せる。

## 公開したときにできること・できないこと

ニコニコのAPIは Snapshot も nvapi も **CORSヘッダを返さない**（ブラウザから
実際に叩いて確認済み。いずれも `Failed to fetch`）。
つまり公開したページからは、候補を1本も増やせない。

| 機能 | 公開サイトの訪問者 |
|---|---|
| 評価・学習・重みの育成 | できる |
| 保留・除外・お気に入り | できる |
| お気に入り投稿者の一覧とニコニコへのリンク | できる |
| プロファイルの書き出し／読み込み | できる |
| 候補プールを増やす | できない（収集側の仕事） |

候補プールは全員に同じものが配られる。
特定の誰かの好みでプールが偏らないよう、
Web側からは収集を促すUIを一切出していない。

`expand`（高評価動画からの類似探索）と `uploader`（お気に入り投稿者の
作品取り込み）はCLIには残っているが、**使うとプールがその人の好みに寄る**。
公開サイト用のプールを作る間は、`ranking` と `tags` だけで回すのが筋。

## デプロイ（Cloudflare Workers）

配信するのは `web/dist`（HTML/CSS/JS ＋ `data/*.json` で 2.3MB 前後）。
Workers の静的アセット配信としてデプロイする。

設定はダッシュボードではなく `web/wrangler.jsonc` に置いてある。

```jsonc
{
  "name": "nicoreco",
  "compatibility_date": "2026-09-03",
  "assets": { "directory": "./dist" }
}
```

Worker スクリプトは持たず、アセットだけを配る構成。
`name` はダッシュボード側の Worker 名と一致させること
（食い違うと別の Worker が新しく作られる）。

Workers Builds の設定は3つだけ。

| 項目 | 値 |
|---|---|
| ルートディレクトリ | `web` |
| ビルドコマンド | `npm ci && npm run build` |
| デプロイコマンド | `npx wrangler deploy`（既定のまま） |

Node のバージョンは `web/.node-version` で固定しているので、
ビルド変数の設定は要らない。

`.github/workflows/collect.yml` が毎日 `web/public/data` を更新して
コミットし、Cloudflare 側がその push を拾ってビルドする。
GitHub Actions 側にデプロイ用のワークフローは要らない。

### 無料枠

| | 上限 | この構成での消費 |
|---|---|---|
| Cloudflare のビルド | 500回/月 | 日1回で約30回 |
| 1デプロイのファイル数 | 20,000 | 23ファイル |
| 1ファイルの最大 | 25 MiB | 最大でも1MB未満 |
| GitHub Actions | 公開リポジトリは無料 | collect が1日数分 |

効いてくるのはビルド回数だけ。収集の頻度とデプロイの頻度は分けて考えられるので、
毎時ランキングまで拾いたくなっても、収集は毎時・コミットは日1回にすれば
ビルド回数は増えない。

### 収集コーパスの保全

`data/nico.db`（80MB超）はリポジトリに入れず、二段構えで持ち越す。

1. **`actions/cache`** — 普段はこちら。速いが、7日間使われないと消える
2. **`corpus` タグのリリースに置いた `nico.db.gz`** — キャッシュが無いときの復元元。
   毎日 `--clobber` で上書きするので、常に最新の1つだけが残る

失っても作り直せるものと、作り直せないものがある。

| 中身 | 失ったら |
|---|---|
| 動画のメタデータ（13万件） | タグ検索で取り直せる（20分程度） |
| 投稿者名（2,800人強） | 取り直せる（1人1リクエストなので50分程度） |
| **ランキングの観測履歴** | **取り直せない**（過去の順位は後から辿れない） |

バックアップを置いている理由は3つ目のためで、これだけは時間をかけても復元できない。
